## 二、经确认属于设计范围的项（不做修改）

以下五项经与我们确认，属于**产品既定设计**：内网环境、默认安全前提下的取舍，原型版本即为此行为，本次不修改。

- **P0-1 / P0-2 / P0-3（无鉴权 + 全地址监听）**
  内网专用产品，默认认为内网可信。`:9000` / `:9001` / `:9010` 不做认证，监听全部地址。这是设计决策，非缺陷。

- **P1-3（启动时清防火墙）**
  靶机需要被中央无障碍访问，启动时清理本机防火墙规则是既定行为，与原型一致。

- **P2-3（`capture_stop` 仅返回布尔值）**
  返回 `{"stopped": true, "legacy": true}` 是**协议契约**。若要返回 `pcap_complete` / `exitcode`
  四态，需要同时改动 agent 侧线协议与 MCP 侧解析，会与存量 Python 1.8.3 靶机不兼容。属协议升级，不在本次范围。

- **P3-1（审计 source_ip 恒为 internal）**
  与原型一致。在无鉴权的设计前提下，来源标识本身不构成安全边界。

## 三、P1-4 日志体积 —— 归因修正

原始报告称「日志无轮转，364MB」。**体积属实，但成因需要澄清**：

实测 `/var/log/socket_server.log` = 380,901,672 字节 / 2,158,148 行，最早记录 2026-03-13。

按内容拆解：

| 内容 | 行数 | 来源 |
|---|---|---|
| 回放开始/完成日志 | 914,743 + 914,741 | **Python 版本历史遗留** |
| 发送数据包失败 | 76,249 | Python 版本历史遗留 |
| 其余 | 约 252,000 | 抓包 649 / 拨测 132 / 升级 758 + 历史杂项 |
| **Go 版本产生** | **81 行** | 自 09:56 起 |

也就是说：**这 364MB 绝大部分是 Go 重构之前 Python 版本写下的**。Go 版的回放模块只在出错时写日志，正常回放不产生任何日志行，不会再出现这个量级。

**结论**：这是历史遗留数据的清理问题，不是 Go 版的日志设计缺陷。加轮转仍有必要（防止将来异常情况下无限增长），但不必按「Go 版日志过多」来对待。

## 四、P1-2 重启空窗 —— 主因已消除

原报告记录「最多断 6 次」。经排查，**主要诱因是 P1-1**：`install` 对无法识别的参数静默忽略后照样执行完整安装流程，其中包含服务重启。真机日志显示 `install --help` 在 15:02 与 20:14 各触发一次重启。

P1-1 修复后，非升级场景不会再出现非预期重启。剩余场景：

- **升级过程的 3~5 秒空窗**：`RestartSec=5` 导致的既定行为，升级后服务需要重新拉起，属设计使然。
- **MCP 侧无重试**：连接失败时直接返回 `"not connected"`。此项列入后续版本，需注意 `cmd_exec` 等非幂等操作不能盲目重试。

## 五、本次已修复（v1.9.5）

### 1. P2-1 MCP 进程运行在已删除的二进制上

**性质**：我方 v1.9.3 引入的回归。

**成因**：为简化安装路径，`/usr/local/bin/socketstack` 由独立副本改为指向 `current/socket_server` 的软链。此后 agent 与 MCP 共享同一个文件；`install` 用 rename 方式覆写时，两者的旧 inode 同时被标记删除。agent 侧已包含重启，MCP 侧在**不带 `--with-mcp`** 的安装中不会被触碰，因而持续运行旧代码。

**影响**：进程实际运行旧版本，而 `status` 显示为新版本号，从外部无法察觉。若新旧版本行为有差异，排查会非常困难。

**修复**：
- `status` 增加二进制一致性检测：读取 `/proc/<pid>/exe` 并与单元 `ExecStart` 指向的文件比对。发现不一致（或指向 `(deleted)`）时明确告警，并给出修复命令。
- `install` 在检测到 MCP 单元正在运行且二进制不一致时，自动重启该单元。**仅重启，不修改任何 MCP 配置**，分机部署不受影响。重启后会再次校验，若仍不一致（典型原因是单元 `ExecStart` 指向别处）会如实告警而非谎报成功。
- 比对基准取单元真实的 `ExecStart`，而不是硬编码路径，避免老机器上的残留配置造成误报。
- 非 root 执行 `status` 时无法读取他人进程信息，此时会明确提示「需 root 才能检测」，而不是静默显示正常。
- **同源问题一并修复**：中央推送升级（`upgrade_run`）切换版本后，原先只重启 agent 单元。同机部署时 mcp 共享同一个二进制文件，会继续跑旧版本。现已在切换后一并重启运行中的 mcp 单元；分机部署（靶机无 mcp）不受影响。

**修复后 `status` 输出**（真机实测，该问题在反馈机器上确实存在）：

```
版本      : v1.9.5
agent 服务: active (socket_server.service)
mcp 服务  : active (socketstack-mcp.service)
  进程跑的是已删除的旧二进制（/opt/socket/versions/1.9.4/socket_server (deleted)）
  修复: systemctl restart socketstack-mcp
```

非 root 执行时（读不到他人进程）：

```
agent 服务: active (socket_server.service)
  需 root 才能检测 socket_server 的二进制漂移
```

修复前该行不存在，用户看不到任何异常。

### 2. P1-1 `install` 忽略参数

**成因**：参数解析只识别 `--with-mcp`，其余一律静默丢弃，随后照常执行完整安装（含服务重启）。因此 `socketstack install --help` 会真的重装并重启服务。

**修复**：
- `-h` / `--help` / `help` → 只打印用法，退出码 0，**不执行任何操作**
- 未知参数 → 打印用法，退出码 2，**不执行任何操作**
- 目前唯一有效参数仍为 `--with-mcp`

**行为变更提示**：此前任意参数都会被接受并执行安装。若你们的自动化脚本中使用了 `install -y` 或其他参数，升级后会被拒绝。请检查脚本。

**同类问题一并修复**（自查时发现的同源缺陷）：
- `uninstall --help` 原先会**真的执行卸载**（停用两个单元、删除 current 软链）。现已改为只打印用法。卸载的破坏性比安装更直接，这一条比 `install` 更值得注意。
- `mcp --help` 原先会掉进阻塞的 stdio 模式，看起来像卡死。现在会打印用法。

两者现在与 `install` 使用同一套规则：help 退出 0、未知参数退出 2、均不执行操作。

### 3. P3-2 systemd 单元无备份

**修复**：覆写单元文件前，先将其重命名保存为 `<文件名>.bak.<纳秒时间戳>`，最多保留最近 3 份；内容未变化时跳过写入；写入失败时自动还原备份。

两处额外的安全约束：
- 备份失败时**放弃覆写**（而不是继续硬写），避免「以为有备份、实际没有」
- 旧文件存在但读不到（权限问题）时直接报错，不会把它当作「不存在」而无备份冲掉

内容未变化时既不写文件也不触发 `systemctl daemon-reload`——这个函数在服务每次启动的单元自愈流程里都会走到。
