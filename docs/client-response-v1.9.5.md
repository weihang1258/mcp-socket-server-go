## 二、经确认属于设计范围的项（不做修改）

以下四项经与我们确认，属于**产品既定设计**：内网环境、默认安全前提下的取舍，原型版本即为此行为，本次不修改。

- **P0-1 / P0-2 / P0-3（无鉴权 + 全地址监听）**
  内网专用产品，默认认为内网可信。`:9000` / `:9001` / `:9010` 不做认证，监听全部地址。这是设计决策，非缺陷。

- **P1-3（启动时清防火墙）**
  靶机需要被中央无障碍访问，启动时清理本机防火墙规则是既定行为，与原型一致。
  具体动作（v1.9.11 起明确写进文档）：`systemctl stop/disable firewalld`、
  `iptables -F -X -Z`、`setenforce 0`。**手工加的防火墙规则会在 agent 每次重启
  后失效**；将来要做网络隔离须依赖靶机上层的 ACL/交换机策略，不能靠靶机本地
  防火墙。

- **P2-3（`capture_stop` 仅返回布尔值）**
  返回 `{"stopped": true, "legacy": true}` 是**协议契约**。若要返回 `pcap_complete` / `exitcode`
  四态，需要同时改动 agent 侧线协议与 MCP 侧解析，会与存量 Python 1.8.3 靶机不兼容。属协议升级，不在本次范围。

> 补充：P3-1（审计来源 IP）原也被归入此项，后来认为它属于**实现缺陷而非设计取舍**——不做鉴权不代表不需要知道谁调的。已在本次修复。

## 三、P1-4 日志体积 —— 归因修正

原始报告称「日志无轮转，364MB」。**体积属实，但成因需要澄清**：

实测 `/var/log/socket_server.log` = 380,901,672 字节 / 2,158,148 行，最早记录 2026-03-13。

按内容拆解：

| 内容 | 行数 | 来源 |
|---|---|---|
| 回放开始/完成日志 | 914,743 + 914,741 | **Python 版本历史遗留** |
| 发送数据包失败 | 76,249 | Python 版本历史遗留 |
| 其余 | 约 252,000 | 抓包 649 / 拨测 132 / 升级 758 + 历史杂项 |
| **Go 版本产生** | **81 行** | 自 09:56 起 |

也就是说：**这 364MB 绝大部分是 Go 重构之前 Python 版本写下的**。Go 版的回放模块只在出错时写日志，正常回放不产生任何日志行，不会再出现这个量级。

**结论**：这是历史遗留数据的清理问题，不是 Go 版的日志设计缺陷。加轮转仍有必要（防止将来异常情况下无限增长），但不必按「Go 版日志过多」来对待。

## 四、P1-2 重启空窗 —— 主因已消除

原报告记录「最多断 6 次」。经排查，**主要诱因是 P1-1**：`install` 对无法识别的参数静默忽略后照样执行完整安装流程，其中包含服务重启。真机日志显示 `install --help` 在 15:02 与 20:14 各触发一次重启。

P1-1 修复后，非升级场景不会再出现非预期重启。剩余场景：

- **升级过程的 3~5 秒空窗**：`RestartSec=5` 导致的既定行为，升级后服务需要重新拉起，属设计使然。
- **MCP 侧无重试**：连接失败时直接返回 `"not connected"`。此项列入后续版本，需注意 `cmd_exec` 等非幂等操作不能盲目重试。

## 五、本次已修复（v1.9.5）

### 1. P2-1 MCP 进程运行在已删除的二进制上

**性质**：我方 v1.9.3 引入的回归。

**成因**：为简化安装路径，`/usr/local/bin/socketstack` 由独立副本改为指向 `current/socket_server` 的软链。此后 agent 与 MCP 共享同一个文件；`install` 用 rename 方式覆写时，两者的旧 inode 同时被标记删除。agent 侧已包含重启，MCP 侧在**不带 `--with-mcp`** 的安装中不会被触碰，因而持续运行旧代码。

**影响**：进程实际运行旧版本，而 `status` 显示为新版本号，从外部无法察觉。若新旧版本行为有差异，排查会非常困难。

**修复**：
- `status` 增加二进制一致性检测：读取 `/proc/<pid>/exe` 并与单元 `ExecStart` 指向的文件比对。发现不一致（或指向 `(deleted)`）时明确告警，并给出修复命令。
- `install` 在检测到 MCP 单元正在运行且二进制不一致时，自动重启该单元。**仅重启，不修改任何 MCP 配置**，分机部署不受影响。重启后会再次校验，若仍不一致（典型原因是单元 `ExecStart` 指向别处）会如实告警而非谎报成功。
- 比对基准取单元真实的 `ExecStart`，而不是硬编码路径，避免老机器上的残留配置造成误报。
- 非 root 执行 `status` 时无法读取他人进程信息，此时会明确提示「需 root 才能检测」，而不是静默显示正常。
- **同源问题一并修复**：中央推送升级（`upgrade_run`）切换版本后，原先只重启 agent 单元。同机部署时 mcp 共享同一个二进制文件，会继续跑旧版本。现已在切换后一并重启运行中的 mcp 单元；分机部署（靶机无 mcp）不受影响。

**修复后 `status` 输出**（真机实测，该问题在反馈机器上确实存在）：

```
版本      : v1.9.5
agent 服务: active (socket_server.service)
mcp 服务  : active (socketstack-mcp.service)
  进程跑的是已删除的旧二进制（/opt/socket/versions/1.9.4/socket_server (deleted)）
  修复: systemctl restart socketstack-mcp
```

非 root 执行时（读不到他人进程）：

```
agent 服务: active (socket_server.service)
  需 root 才能检测 socket_server 的二进制漂移
```

修复前该行不存在，用户看不到任何异常。

### 2. P1-1 `install` 忽略参数

**成因**：参数解析只识别 `--with-mcp`，其余一律静默丢弃，随后照常执行完整安装（含服务重启）。因此 `socketstack install --help` 会真的重装并重启服务。

**修复**：
- `-h` / `--help` / `help` → 只打印用法，退出码 0，**不执行任何操作**
- 未知参数 → 打印用法，退出码 2，**不执行任何操作**
- 目前唯一有效参数仍为 `--with-mcp`

**行为变更提示**：此前任意参数都会被接受并执行安装。若你们的自动化脚本中使用了 `install -y` 或其他参数，升级后会被拒绝。请检查脚本。

**同类问题一并修复**（自查时发现的同源缺陷）：
- `uninstall --help` 原先会**真的执行卸载**（停用两个单元、删除 current 软链）。现已改为只打印用法。卸载的破坏性比安装更直接，这一条比 `install` 更值得注意。
- `mcp --help` 原先会掉进阻塞的 stdio 模式，看起来像卡死。现在会打印用法。

两者现在与 `install` 使用同一套规则：help 退出 0、未知参数退出 2、均不执行操作。

### 3. P3-2 systemd 单元无备份

**修复**：覆写单元文件前，先将其重命名保存为 `<文件名>.bak.<纳秒时间戳>`，最多保留最近 3 份；内容未变化时跳过写入；写入失败时自动还原备份。

两处额外的安全约束：
- 备份失败时**放弃覆写**（而不是继续硬写），避免「以为有备份、实际没有」
- 旧文件存在但读不到（权限问题）时直接报错，不会把它当作「不存在」而无备份冲掉

内容未变化时既不写文件也不触发 `systemctl daemon-reload`——这个函数在服务每次启动的单元自愈流程里都会走到。

### 4. P1-4 日志轮转

**修复**：`install` 在 `/etc/logrotate.d/socketstack` 写入轮转配置：`size 60M`、保留 5 份、压缩。

使用 `copytruncate` 而非 `create`：agent 由 systemd 常驻并长期持有日志文件句柄，`rename` 之后它仍会写入旧 inode，必须就地截断。

**已知代价**：`copytruncate` 在「拷贝完成、截断生效」之间写入的日志行会丢失。agent 是重日志源，这个窗口里丢几行并非不可能。彻底解决需要 agent 支持收到信号后重开日志文件，再改用 `create` + `postrotate`；那要动 agent 侧，本次不做。

配置写入失败只告警，不中断安装。`uninstall` 会一并移除该配置（它由 `install` 生成，属纯运维副作用文件，与「保留配置/数据库」不同类）。

**关于历史日志**：现有 364MB 不会被自动清理（这是数据，我们不替你删）。需要时手动处理：

```bash
sudo truncate -s 0 /var/log/socket_server.log     # 直接清空
# 或先归档再清空
sudo cp /var/log/socket_server.log /tmp/socket_server.log.$(date +%F)
sudo truncate -s 0 /var/log/socket_server.log
```

### 5. P1-2 连接重试

**修复**：连接建立失败时退避重试 3 次（500ms 起，逐次翻倍）。错误文案也从裸 `not connected` 改为「连接 <地址> 失败（已重试 N 次，靶机可能正在重启，请稍后重试）」。

**关键边界**：**只重试建连，绝不重试已经发出的请求**。`cmd_exec` 这类操作非幂等，重发会执行两次。因此：
- 工具调用（`cmd_exec` / `capture_start` 等）走连接池，建连失败会重试
- `upgrade_run` 的版本轮询刻意**不重试**——它本身每 3 秒轮询一次，若每次再重试 3 次会把节奏拖慢 6 倍，180 秒的确认窗口只够跑 10 轮

### 6. P3-1 审计来源 IP

**修复**：HTTP 传输层增加中间件，把调用方 IP（`X-Forwarded-For` 优先，否则 `RemoteAddr`）写入请求 context，三处审计写入改为取真实来源。stdio 模式（本地无 HTTP 来源）仍记录为 `internal`。

中间件必须包在 SDK 的 Streamable HTTP handler **外层**——go-sdk 用 `req.Context()` 建会话，只有外层的值才能传到工具处理函数。

> 说明：这原被归类为「与原型一致的既定行为」，重新评估后认为是**实现缺陷**——不做鉴权不等于不需要知道是谁调的。现在审计日志里能看到真实 IP。

> 限制：会话值在建会话那次请求（`initialize`）时取定。本产品一个会话即一个客户端，不影响语义；若日后在前后加按请求轮换的代理，审计 IP 会固定成第一跳地址。

## 八、v1.9.6 —— 验收反馈修复

第一轮验收暴露了四项，均已修复。

### 1. `upgrade_run` 不重启 mcp（验收实测未生效）

**这是 v1.9.5 的回函说了、但代码没做到的一条。** 验收记录「agent PID 93361 → 112201，mcp PID 92788 始终未变」完全属实。

**成因**：`switchTo` 里 mcp 重启排在 `restartServiceFn()` 之后，而后者是 `systemctl restart <socket_server 自己>`——它会把本进程杀掉，排在后面的那行**永远执行不到**。回函写的时候代码就是这么排的，测试也没发现，因为测试里 `restartServiceFn` 是个不杀进程的桩。

**修复**：把 mcp 重启移到 agent restart **之前**。新增测试 `TestSwitchToRestartsMCPBeforeKillingSelf`，模拟「restart 之后任何语句都不可能执行」，把顺序锁死。

**真机复验**（v1.9.6）：对 127.0.0.1 执行 `upgrade_run` → mcp PID 136892 → 137287、agent PID 136850 → 137295，两者都重启了。

### 2. `upgrade_run` 审计丢失失败原因

**成因**：`upgrade_run` 自己拼 `outcomes` 时只写 `{"target":…,"ok":false}`，没有 `error` 字段，与 `writeAudit` 的格式不一致。所以那条 47ms 的失败在审计里只剩 `ok:false`，原因彻底丢失。

**修复**：补上 `error` 字段（成功记空串，失败记 reason）。

> 关于那个 47ms 失败本身：修复后按同样步骤（先升 `127.0.0.1` 再升 `10.12.131.35`）**未能复现**，两次都正常（各 ~4.4s）。当时的审计没留原因，现在也无法回溯。可能在 1.9.6 下已不复现，但**没有确证**。若再次出现，v1.9.6 的审计会带上具体原因，可以直接定位。

### 3. `install` 无条件跑 apt-get、拿不到锁就白等

**成因**：`apt-get install` 在 dpkg 锁被占用时默认无限等锁。install 因此白等一整轮，最后只留一句警告，而**退出码仍是 0**，自动化无法判断依赖是否真的装好。

**修复**：apt 分支加 `-o DPkg::Lock::Timeout=0`，拿不到锁立刻失败。yum/dnf 不加（无此问题）。

**需要说明的边界**：退出码仍是 0。这是 Python `install.sh` 的既有契约（依赖装不上不阻断安装），我们保持了它。依赖是否装好要看 stderr 的告警文本。

> **v1.9.7 已彻底解决**：`install` 不再调用包管理器（见§九），此边界不复存在；显式安装浏览器依赖的 `deps install-browser` 失败即非 0 退出。

### 4. 版本目录只增不减

**修复**：`switchTo` 成功后清理到最近 3 个版本（含当前），`current` 指向的版本永不删。按版本号排序，不是按 mtime（推送升级可能补装旧版本）。

**真机效果**：28 个版本 387MB → 3 个版本 43MB。

### 关于「同机自升级打断 MCP」

验收建议在文档里写明「无法用 MCP 给 MCP 自己所在的那台机推升级」。经复测，**该限制未能在 v1.9.6 上复现**：同一会话连续对 `127.0.0.1` 与 `10.12.131.35`（本机地址）执行 `upgrade_run` 均成功。

原因：MCP 进程与被升级的 agent 是两个独立进程，agent 重启不影响 MCP 自身的 HTTP 服务；只有 `switchTo` 里那句「顺带重启 mcp」会中断 MCP——而这正是第 1 条修掉的行为（现在 mcp 在 agent 重启前有序重启，重启完成后再没有对 MCP 的干扰）。

如果你们在 v1.9.5 上遇到 `unexpected end of JSON input`，那大概率就是 v1.9.5 这个顺序 bug 的连带效果。若在 v1.9.6 上仍能复现，请把审计里那条 `upgrade_run` 的 `error` 字段发给我们——现在它会被记录下来了。

## 九、v1.9.7 —— 去外部依赖 + 日志保留策略

### 1. `route` / `ifconfig` / `ethtool` 改为内核接口原生实现

这三个命令本身只是内核接口的薄封装（`route -n` 读的就是 `/proc/net/route`，ifconfig 的 MTU 走 SIOCGIFMTU/SIOCSIFMTU，ethtool 的队列查询/设置走 SIOCETHTOOL）。现在 agent 直接调内核接口，不再执行这三个外部命令。

真机对拍（同机逐字段比对）：

- 原生 routeinfo 输出与 `route -n` 解析结果完全一致（含点分十进制、UG/U 标志、Metric）
- MTU 读数与 `/sys/class/net/*/mtu` 一致；设置在 root 下完成 1500↔65536 往返
- 网卡队列读数与 `ethtool -l` 一致（本机 eno4 当前 combined=1）

**行为差异**（有意变更，见设计文档 §12 #53）：dt10 原「ifconfig 缺失 → 断连」变为「MTU 查询失败 → 断连」——网卡不存在时行为相同；设置失败仍吞错（对齐 Python exec 语义）。

### 2. `install` 不再调用包管理器

原先每次 install 都会执行 apt/yum 装两批包：ethtool + net-tools、chromium 的二十多个运行库。前者已因原生实现无必要；后者只有**浏览器拨测**（boce_run 浏览器模式）用得着，抓包/回放/命令执行完全不需要。

这正是验收发现的「install 白等 dpkg 锁」的主要来源。现在：

- `socketstack install` 只装服务本身，内网无软件源的机器不再有等待
- 需要浏览器拨测的机器，显式执行 `sudo socketstack deps install-browser`
- `deps install-browser` **失败以非 0 退出**（不再警告后照常成功）；apt 拿不到锁立即失败（DPkg::Lock::Timeout=0）
- 缺库诊断仍保留：`status` 会列出 chromium 缺哪些 `.so` 并给出修复命令

### 3. 日志保留 7 天

logrotate 配置改为：`daily + maxsize 60M + maxage 7 + rotate 7 + copytruncate + compress`。每天轮转、单日超 60M 提前轮转，超过 7 天的归档由 logrotate 自动删除，不再永久累积。

（说明：最初写的是 `size 60M`，上线前干跑发现 size 是绝对条件、会覆盖 daily——日志不涨满 60M 就永不轮转，7 天保留失效。已改用 `maxsize`：到期照轮、超限提前。）

历史处置：清空日志时保留在 /tmp 的 364MB 归档已按「只留 7 天」原则删除（其中 99% 是 3 月～10 月的 Python 时代日志）。当前 /var/log 下只有 7 天内的两份小文件。

### 4. 未动的两项（经评估不做伪替代）

- **tcpdump**：agent 只用它把用户填写的过滤表达式编译成内核 BPF 指令（`tcpdump -ddd`），并不用 tcpdump 抓包。自行手写 BPF 编译器一旦语义有偏差，会「静默抓错包」，比保留这个依赖危险得多。系统普遍自带 tcpdump，不进安装清单。
- **chromium 本体**：普通 HTTP 客户端不能执行页面 JS、不能模拟浏览器重定向/弹窗，用它冒充拨测会让「拨测成功」失去意义。需要无库部署时，方向是把带完整运行环境的浏览器做成独立组件包，单独评估。

## 十二、中央下载失败根因 —— 配置写在错误层级，静默失效（五轮验收定论）

## 十四、v1.9.12 → v1.9.13 —— 靶机重启瞬间并发失败（P2，含我方结论更正）

v1.9.12 回函断言「重启瞬间至多在途 1 条失败」，**验收复测证伪（7/7 复现并发 N 条全败），本节如实更正**，并依据真机实测把机制讲清。

### 1. 机制更正：重启瞬间的并发全败是「请求在途」的物理失败，不是复用错判

我们用与验收完全一致的场景做了系统实测（真 MCP `:9010`、真靶机 82、
`systemd-run --on-active` 定时重启、5 路栅栏齐发、按「齐发时刻相对 TERM
的偏移」从 -300ms 扫到 +300ms 共 12 组，v1.9.12 与 v1.9.13 两版对照）：

- **TERM 后任何 ≥ 几毫秒发起的调用都能毫秒级自愈**：靶机 agent 无优雅
  关停（SIGTERM 即死），FIN 亚毫秒到达中央、`systemctl restart` 的
  停→起间隙 <300ms。v1.9.12 的 1ms 读探针在这些时刻全部正确判死、
  新建即成功——12 组偏移实测 **0 失败**（两版同）。
- **验收 7/7 复现的「并发 N 全败 + 裸 EOF」只能发生在另一种情形**：5 路
  请求已发出、响应未回的毫秒级窗口内进程恰好死亡（请求在途跨 TERM）。
  这与连接池、探针均无关——**请求已发出，服务端没了，任何客户端都救不了**。
  失败条数 = 在途并发数，故「并发 N → 全败 N」。我方此前「至多在途 1 条」
  的说法撤回；v1.9.12 探针在这个场景里确实无能为力，但根因不是探针判活
  误判（该窗口在真机 <1ms），而是「请求已发出」这一物理事实。
- 探针误判复用（读探针在 FIN 传播窗内判活→复用→EOF）在原理上存在，但
  实测该窗口在现网 <1ms，**不是**验收 7/7 的主因。

### 2. v1.9.13 的三处改进（如实定位各自的价值）

1. **复用前 dial 验证**：弹出空闲连接后，除读探针外再对靶机做一次
   TCP 握手（300ms 上限，不发数据）。进程死=监听 socket 关=新 SYN 即刻
   RST，不受 FIN 传播影响——原理性堵死「探针判活但服务端已死」的复用路径。
   代价是每次复用多一次建连握手（局域网 <1ms，有意取舍，见设计文档 §12）。
2. **判死后不再报错，改走新建**：dial 判死的复用连接被丢弃后直接落入
   新建路径，由建连退避重试（3 次、500ms 起翻倍）自然吃掉 restart 间隙；
   只重试**建连**、绝不重发请求（cmd_exec 非幂等边界不变）。
3. **在途失败的文案语义化**：对已发出请求遇到 EOF/reset 的场景（即验收
   复现的「裸 EOF」），错误文案从裸 `EOF` 改为
   `靶机连接已断（靶机可能正在重启，请稍后重试）: EOF`——真实原因保留在
   尾部，现场可判读「等一秒重试即可」。

### 3. 对「重启瞬间」的如实预期（验收方可按此验收 v1.9.13）

- 请求在途跨 TERM 的调用：**仍会失败，且条数 = 在途并发数**——这是物理，
  我方不再承诺消除；文案为第 3 条的可判读形式。
- TERM 后发起的调用：探针 + dial 双重校验后新建，正常返回；restart 间隙
  内的调用由建连重试兜住（间隙 <300ms，实测无感）。
- 静默超时契约不变（超时=空响应，Python 语义）。

### 4. 验证方式

- 单测（`-race` 全绿）：`TestAcquireDialCheckRejectsReuseWhenListenerClosed`
  （listener 已关、旧连接仍 ESTABLISHED 的 FIN 窗口模拟 → 弃复用走新建）、
  `TestRunBatchEOFGetsFriendlyText`（accept-then-close = 请求在途服务端死 →
  断言语义化文案）、`TestPoolAcquireSkipsDeadIdle`、`TestRecvUntilTimeoutErrorNotSwallowed`。

### 5. 顺带发现（提示项）

并发压测**同一靶机的 `cmd_exec`** 时，MCP 侧有「锁类 shell 冲突」串行化
保护（同靶机同时只放行 1 条，其余直接拒绝）——这是设计行为（防止并发

## 十六、v1.9.15 —— 非幂等命令在途失败文案引导重复执行（P2，含根因复盘）

### 1. 现象与复现（真机实测确认）

验收复现命令（真 MCP `:9010`，靶机 82，v1.9.14）：

```
cmd_exec: rm -f /tmp/idem4.txt; systemd-run --on-active=10 \
  --timer-property=AccuracySec=1s systemctl restart socket_server >/dev/null; \
  echo S >> /tmp/idem4.txt; sleep 30; echo E >> /tmp/idem4.txt
```

命令在途跨过靶机重启 → MCP 返回
`"靶机连接已断（靶机可能正在重启，请稍后重试）: EOF"`，而靶机文件里
**只有 S**——命令已部分执行。此时文案里的「请稍后重试」是在引导把
非幂等命令再执行一遍：对 cmd_exec 承载的升级/配置下发/重启类操作，
重复执行后果不可控。我方按同一场景复现成功（文件只含 S），确认属实。

### 2. 为什么反复出问题 —— 三个层面的根因复盘

这条缺陷是我方 v1.9.13 自己引入的（Python 版只冒泡裸异常、从不给建议），
七轮验收把它照了出来。复盘为什么连修三轮还在出：

1. **修复停留在上报层，没到消费层**。v1.9.12~13 修的是「错误怎么呈现」
   （裸 EOF → 语义化文案），但没问「拿到这条错误的人会做什么」。对只读
   工具，「请稍后重试」是正确的下一步；对 cmd_exec，同样的字是危险指令。
   文案本身就是一个 API，却从未按工具语义区分过。
2. **统一处理掩盖了语义差异**。connErrText 在 runOne 对**所有**工具套同
   一句话——一次修复、全量生效的写法，恰好把「幂等/非幂等」这个工具间
   最关键的差异抹平了。
3. **测试从未断言过文案与工具的匹配**。此前测试只断言「文案含某某字样」，
   不区分它出现在哪个工具的返回里——错误文案对哪个工具说了什么，一直
   没有测试锁定。本次起测试按档断言（见下）。

### 3. 修复（v1.9.15）：文案按工具幂等性分档

`runBatch` 增加显式 `retrySafe` 参数，每个工具调用点必须表态（编译期强制，
不靠名字推导——version/isfile/isdir 不写审计、upgrade_run 同样没有可推导
的标记）：

| 档 | 工具 | 文案 |
|---|---|---|
| 重发安全 | version、isfile、isdir、pcap_flow_extract、capture_stop | `靶机连接已断（靶机可能正在重启，请稍后重试）: EOF`（不变） |
| **状态未知** | **cmd_exec**、capture_start、boce_run、replay_run、socket_listen、upgrade_run | `靶机连接已断（靶机可能正在重启；命令执行状态未知——可能已部分执行或已完成但响应丢失，请先核实副作用，勿直接重试）: EOF` |

真实原因仍保留在尾部。对 cmd_exec 的核实手段现成：文件类副作用用
`isfile`/`cmd_exec` 查目标文件状态，服务类用 `version` 探活——核实后再
决定是否重发，而不是被文案推着重发。

「成功与不知道在返回体上不可区分」「耗时判读不了」两条属协议层契约
（dt1 成功路径本就只回 stdout，无执行回执），改它要动 agent 侧线协议，
不在本次范围；文案分档已把「不可判读」三重里最危险的一重（引导重试）消除。

### 4. 验证

- 单测（`-race` 全绿）：`TestRunBatchConnLostNonIdempotentText`（cmd_exec 档
  EOF → 必含「执行状态未知/勿直接重试」、必不含「请稍后重试」）、
  `TestRunBatchEOFGetsFriendlyText`（version 档保持可重试文案）。

| 出口 | 情形 | 非幂等（cmd_exec 等） | retry-safe（version 等） |
|---|---|---|---|
| **A 建连失败** | 请求未发出，命令**必然未执行** | `pool: 连接 … 失败（已重试 3 次，靶机可能正在重启）: dial … refused`**`（连接未建立，请求未发送执行，未产生副作用；可稍后重试）`** | `…refused（请稍后重试）` |

### 4. 对 §五「ok=1/code=0/5ms」观察的自查结论

桥接层不存在「靶机不可达却报成功」的路径：`cmd_exec` 的 ok=1 只能来自 dt1

connectWithRetry 三次退避（500ms+1s）必然把耗时拉到 ≥1.5s（验收自己的
1.503s 失败样本即如此）。

### 缺陷与修复（v1.9.18）：cmd_exec wait=false 丢失 B18 note

**现象**：wait=false 回执 `results` 只有 target，无 note。Python 版此处回执带
`wait=false 为异步执行不返回回显…` 提示。

**根因**：Go 的 typed-nil——`fn` 直接 `return c.CmdExec(...)`，客户端返回的
nil map 装进 `any` 后是 typed nil，`runOne` 的 `case nil` 不匹配、落入
`case map[string]any` 后 `v==nil` 落空（range 空 map 无键），B18 note 成为
死代码。v1.9.15~17 的分档/映射测试均未覆盖此路径——正常路径回归此前只测过
wait=true。

**修复**：typed nil map 与裸 nil 同义处理；回归测试
`TestRunBatchTypedNilGetsNote`（typed nil → note 必现）。v1.9.18 双机部署后
真机复验：wait=false 回执带 note ✅。

### 回归中的两个「看似异常、实为契约」项（免复查）

1. isfile/isdir 对不存在路径记 `failed: agent 返回 False（业务失败）`——

2. socket_listen 在 stop 后 clean 返回错误——agent 侧 `listenClean` 未启动
   即裸 `b"error"`（handlers.py 逐字复刻）；正确时序见工具描述
   （start→…→save/fetch 须在 stop 之前）。

## 二十、v1.9.19 —— 出口 A 细分两型与文案前缀统一（2026-11-02）

对验收 v1.9.18 复测（N1–N8 全过）提出的三条跟进项，全部属实并已处置。

### 1. P1 池满误并建连失败档 —— 属实，已细分（v1.9.19）

验收判定准确：`pool.Acquire` 的「连接池满，等待超时」与建连失败同为「请求
未发出」，但语义不同——池满=**靶机健康、并发占满**（处置：调并发/等释放），
建连失败=**靶机不可达**（处置：等恢复）。v1.9.17 把两者都交给 `dialErrText`
统一套「连接未建立…」话术，混淆了两种处置。

修复：`dialErrText` 按错误文本分型（wire 错误无类型，与 `isConnLost` 同法）：

| 情形 | 非幂等 | retry-safe |
|---|---|---|
| 建连失败 | `…refused（连接未建立，请求未发送执行，未产生副作用；可稍后重试）` | `…refused（请稍后重试）` |
| **池满** | `靶机 X 连接池满，等待超时（请求未发送执行，未产生副作用；可稍后重试）` | `靶机 X 连接池满，等待超时（请稍后重试）` |

池满两档均不出现「连接未建立」。

### 2. P2 「pool: 」前缀不一致 —— 属实，已删除（v1.9.19）

`"pool: "` 只出现在 runOne 出口 A 一处（既非按通道分、也非按出口分），删除；
档位信息由 `dialErrText` 尾注承载。至此两通道（runOne/Sched.Batch）、两出口
（A/B）的失败文案均无人工前缀，映射测试已加「不得带 pool: 前缀」断言锁定。

### 3. 池满真机触发（验收未构造成功，本轮补上）

同靶 6 路并发 `pcap_flow_extract`（无锁类、走 Sched.Batch，连接池上限 5）+
大目录拉长单次提取（4KB×10 万文件）：5 路占满连接池，第 6 路 10 秒借用超时
命中池满，真机返回：

```
{"reason":"靶机 10.12.131.82 连接池满,等待超时（请稍后重试）","target":"10.12.131.82"}
```

池满+非幂等档的组合无法真机构造（runOne 侧全部工具持锁类，同靶并发先被
锁拒绝、到不了池），由单测 `TestDialErrTextKinds` 四象限锁定（建连失败/池满
× 两档，各断言必含与必不含）。

### 修复过程（两连发，如实记录）

**v1.9.20**：`RunStreamableHTTP` 改为显式双条绑定（`0.0.0.0:port` + `[::]:port`，
v6 失败降级仅 v4，与 :9000/:9001 同策略）。真机部署后发现一个隐式行为：
`net.Listen("tcp", "0.0.0.0:p")` 在 Go 里实际生成 **AF_INET6 双栈通配 socket**
（ss 显示 `*:9010`，v4-mapped 收 v4）——运行时结果已是双栈（v4/v6 实连均通），
但我的 `[::]` 第二条被 EADDRINUSE 降级、日志打出误导性的「降级为仅 IPv4」。
**v1.9.21**：v4 侧改显式 `tcp4` 绑定，与 :9000/:9001 的分绑方式完全一致，
行为可预期、日志如实（双栈）。
