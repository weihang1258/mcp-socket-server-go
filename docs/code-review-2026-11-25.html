P1 阻断级：真机上会出事

这六项不是理论风险。其中两项的后果已经在 82 上直接观察到：进程内存常年 1GB，以及一台单 CPU 的机器被算成「应该绑到 CPU7」。

编号 / 位置问题（白话）影响最优方案
P1-1agent/server.go:58

代理端收一帧时，帧头里写着多长就按多长收，不核对上限。

内存跟着对方报的数字涨。82 上这个进程平时就占 1GB，再撞上一次就是被系统杀掉，同一台机器上的所有连接一起断。

帧头加一道 256MB 上限，超了直接断连并记日志。别指望 recover 兜住——OOM 是进程级的，recover 管不到。
P1-2agent/capture.go:484

停抓包后要重排时间戳：把整个 pcap 读进内存，再拼一份完整副本写盘。

峰值内存约等于文件大小的两倍。抓五分钟出一个 1GB 的文件，这一下要 2.1GB；设备内存本来就紧。

改成两遍流式：第一遍只记时间戳和偏移，第二遍按偏移顺序抄写。退一步，先把缓冲区预分配好，别逐包 append。
P1-3agent/capture.go:92-99

同一路径已有抓包在跑时，新请求会先停旧的；但不管旧的停没停成功，登记表都删掉。

旧线程还活着却再也停不掉，新的抓包写同一个文件，两个线程同时写——pcap 交错损坏。拿去对比就是全错，而且看不出原因。

只有确认停掉才删登记。没停掉就直接返回失败，不允许在同一路径开新的。
P1-4agent/capture.go:256 / 272 / 564

三条收尾路径都能关到同一个 socket：网卡 down 时、正常收尾时、停止超时强制关时。

第二次关闭时 fd 号可能已被别的连接复用，等于把别人的连接关掉。AF_PACKET 关闭还有约 28ms 的内核同步开销。

给句柄加 sync.Once——和停止状态那套同一个写法。一次关，之后都是空操作。
P1-5bridge/protocol.go:908

桥这边取文件，压缩后的长度超过 1GB 直接报「下载长度异常」。另外解压之后不设上限。

367MB 的 pcap 压完约 120MB，还有余量；但两个 G 级以上的原始文件就撞线，报错文案只说「长度异常」，看不出该换通道。解压不设限则意味着一个很小的压缩包能撑出几十 GB。

上限改成配置项（默认 4GB），错误里直接写「改用 :9001 分段下载」。解压侧同步加界。
P1-6agent/pcapflow.go:79

提五元组时，目录里所有 pcap 全部解析、全部累积进内存、全部序列化传回桥，桥这边才截到 1000 条。

目录一大就 OOM 或者撞 30 秒超时；算完的 99% 在桥侧被直接丢掉，白算。

靶机侧设 20 万条上限，达到就早停，回包带 truncated。桥侧照旧截到 1000。

P2 隐患：特定条件下触发

平时不响，出事时又很难从现象反推原因。P2-1 就是上次 pcapdump 卡死排查绕远路的那类问题。

编号 / 位置问题（白话）影响最优方案
P2-1agent/httpfile.go:365

往客户端发文件的返回值被忽略了。

客户端中途断、磁盘读错，服务端日志一片空白。上次排查 pcapdump 卡死，正是因为日志什么都没有，只能从别处绕。

检查返回值，失败至少记一条日志：路径 + 已发字节数 + 错误原因。
P2-2agent/httpfile.go:443

上传写完不检查关闭是否成功，直接把临时文件改名成目标文件。

磁盘满时数据可能还没刷完，改名却成功了——半截文件被当完整文件收下，调用方还收到 ok:true。下次对比拿这份残包当基准。

检查关闭错误；失败就删掉临时文件、返回 500。
P2-3agent/capture.go:691

网卡绑到哪个 CPU 记下来就再也不删。

网卡删了重建，旧绑定还占着；网卡 A 拔掉后它占的 CPU 不会让给 B。影响面受网卡数量限制，但语义是错的。

抓包结束时按引用计数释放，同一网卡多路径抓包也不冲突。
P2-4agent/capture.go:773 / 787

按 /sys 里的目录个数算机器有几个 CPU，不看当前进程实际能用哪几个。

82 实测只有 cpu0 可用（nproc=1），代码却算出 CPU7 写进中断亲和——内核拒绝或静默无效，日志还打「已绑定到 CPU7」，按日志排查会被带歪。

改用 SchedGetaffinity 拿真正可用的 CPU 集合，只在集合里挑。
P2-5bridge/dpi_ops.go:702 · bridge/tools.go:399

同一模块里两套版本比较：一套按点和横线切、补零到 7 段、带字母权重；另一套只认 1-4 段纯数字、按前缀比。

遇到 1.9.26-rc1 这类字符串，升级判断和兼容判断可能得出相反结论。

合成一套，保留完整语义；兼容判断改成调用同一个函数。
P2-6bridge/bridge.go:24

代码里定义了「文件读写」这一档锁，实际 file_get / file_put 全走无锁。

两个人同时往同一个远端路径上传，后者覆盖前者，谁都没提示。

按远端路径加锁——和抓包那套按 path 加锁同一个思路，keyed 锁。
P2-7bridge/contract.go:126

五元组提取的默认超时只给 30 秒。

大目录必然超时，错误还表现为「超时」而不是「目录太大」，现场容易误判成网络问题。

默认提到 120 秒，工具描述里写明：大目录请按用例目录分次提取。
